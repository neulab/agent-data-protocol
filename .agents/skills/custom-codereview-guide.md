# Agent Data Protocol — Code Review Guidelines

When reviewing this repository, be strict about dataset correctness and reproducibility. The repository's durable contribution rules live in `AGENTS.md`; read that file before reviewing any PR that touches `datasets/`, `agents/`, `schema/`, `scripts/`, or validation tests.

## Required Checks for Dataset PRs

For every dataset addition or dataset-format change, verify that the PR follows all applicable guidelines in `AGENTS.md`. In particular, check that:

- Required files are present: `README.md`, `extract_raw.py`, `raw_to_standardized.py`, `schema_raw.py`, `sample_raw.json`, `sample_std.json`, and root-level `sample_sft.json`.
- Top-level dataset JSON files are limited to `sample_raw.json`, `sample_std.json`, `sample_sft.json`, and `generated_thoughts.json`.
- Sample files are generated by committed scripts and are not hand-patched fixtures. If sample JSON changed but the corresponding generator bug was not fixed, flag it.
- `sample_raw.json`, `sample_std.json`, and `sample_sft.json` represent the same records and preserve IDs/order where applicable.
- `schema_raw.py` validates `sample_raw.json` and standardized trajectories validate against the ADP schema.
- Every `ApiAction.function` exists in the dataset's `api.py`, and every `kwargs` object satisfies that function's signature.
- SFT messages containing `<function=`, `<function_calls>`, or `<invoke name=` use `"from": "function_call"`.
- `TextObservation.source` uses only schema-supported values: `user`, `agent`, or `environment`.
- Dataset-local converters, duplicate API definitions, filtering, dropped actions/observations, or schema changes are clearly justified.
- Large corpora, full generated files, temporary chunks, caches, screenshots, and scratch JSON are not committed.
- Pre-commit hygiene is maintained: formatting, imports, trailing whitespace, and EOF newlines.

## PR Description Requirements

Dataset PR descriptions must include a design-decision catalog for unclear implementation choices. If this is missing, vague, or does not include concrete examples and rejected alternatives, request changes.

Each design decision should include:

1. the ambiguity or question,
2. the chosen approach,
3. a concrete example from the dataset or code, and
4. alternatives considered and why they were rejected.

Examples of decisions that should be cataloged include handling system prompts, failed trajectories, unavailable tools, missing final messages, screenshots, rewards, metadata, action parsing, and filtering criteria.

## Review Style

- Prefer actionable, must-fix comments over broad suggestions.
- Distinguish correctness issues from optional style improvements.
- Do not accept a promise to fix dataset alignment later; the PR should follow current ADP conventions before merge.
- If the PR is generated by an AI agent or the review itself posts human-readable content, include a short disclosure in the review body that the review was generated by an AI agent.
